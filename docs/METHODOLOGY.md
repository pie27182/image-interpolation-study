# Методология экспериментального исследования

## Цель и вопрос

Сравнить качество реконструкции и вычислительную эффективность фиксированных алгоритмов интерполяции при увеличении реальных цифровых изображений в одной программной среде.

Вопрос: как меняются PSNR, SSIM и время выполнения при замене Bicubic на Bilinear, Lanczos, MKS2013 и MKS2021 при одинаковых входах, целевом размере, библиотеке и оборудовании?

Выводы относятся к выбранному датасету и протоколу. Эксперимент не ставит целью доказать, что один метод лучше для любых изображений.

## Baseline

Baseline — Bicubic, реализованный Pillow Image.Resampling.BICUBIC. Документация Pillow указывает BICUBIC как фильтр по умолчанию для Image.resize() на обычных режимах изображений (кроме режимов 1 и P). Это практически значимый baseline для выбранной реализации, а не универсальный default всех графических библиотек.

В коде фильтр задаётся явно, чтобы результат не зависел от поведения аргумента по умолчанию.

## Методы

1. Bilinear — линейная интерполяция по соседним отсчётам; ориентир по скорости и сглаживанию.
2. Bicubic — кубическая интерполяция; baseline.
3. Lanczos — оконная sinc-интерполяция.
4. MKS2013 — Magic Kernel Sharp, вариант 2013 года.
5. MKS2021 — более поздний вариант Magic Kernel Sharp.

Все фильтры вызываются через одну официальную реализацию Pillow Image.resize(). Ядра вручную не переписываются. Pillow 13.0.0 закреплён в requirements, поскольку эта версия добавила MKS2013 и MKS2021. Само наличие фильтра в API подтверждает его практическую доступность, но не доказывает его превосходство.

## Датасет и параметр эксперимента

Используется официальный DIV2K validation: до 100 реальных фотографий высокого разрешения и парные LR изображения. Основной коэффициент увеличения фиксирован: ×4. Для каждой LR-картинки целевой размер равен размерам соответствующей HR-картинки.

Данные DIV2K/NTIRE широко применяются для исследования single-image super-resolution и содержат реальные изображения с известной парной структурой HR/LR. В отличие от случайных паттернов, это фотографии с естественными текстурами и границами.

### Ограничение деградации

Официальные LR-версии DIV2K получены bicubic downsampling. Поэтому оператор деградации согласован с Bicubic и потенциально смещает сравнение в его пользу. Реальная камера создаёт другую деградацию: оптика, фокус, смаз движения, шум матрицы, демозаика, JPEG и неизвестный ресайз. Результат нельзя без дополнительной проверки переносить на камеры видеонаблюдения или OCR. DIV2K — контролируемый benchmark, а не универсальная модель камеры.

## Метрики качества

Скрипт считает:
- PSNR — отношение максимальной мощности сигнала к среднеквадратичной ошибке (dB);
- SSIM — структурное сходство;
- обе метрики по яркостной компоненте и по RGB.

Luma рассчитывается как 0.299 R + 0.587 G + 0.114 B на шкале 0–255 (BT.601-style). Это нужно обозначать именно как luma approximation, а не утверждать полную идентичность MATLAB im2ycbcr/Y-channel реализации.

Перед метриками отбрасывается рамка 4 пикселя (border shave = scale). Это применяется одинаково ко всем фильтрам. Значение сохраняется в run_metadata.json.

## Время выполнения

Основная среда — CPU runtime Google Colab. GPU не используется: фиксированные фильтры вызываются через Pillow и измеряются на CPU.

Протокол:
- декодировать LR и HR до старта таймера;
- для каждого фильтра выполнить один прогревочный вызов;
- выполнить пять измеряемых вызовов;
- сохранить медиану и стандартное отклонение;
- дополнительно нормировать время на количество выходных мегапикселей.

Таймер охватывает только Image.resize(); файловый ввод-вывод, метрики, графики и скачивание данных исключены. Для сопоставимости методы должны запускаться в одном runtime без смены оборудования, версии пакетов, входных данных, масштаба и количества повторов. Тип машины, версия Python, число CPU и версии зависимостей записываются в JSON.

Энергопотребление и пиковая память не заявляются. Colab не предоставляет стабильный переносимый измеритель энергии CPU для всех VM. tracemalloc не видит все нативные аллокации библиотек на C; точное сравнение памяти потребовало бы отдельного запуска каждого метода в изолированном процессе с системным мониторингом.

## Статистический анализ

Единица наблюдения — изображение. Для каждого фильтра по каждому изображению получаются метрики и время. Для каждого метода, кроме Bicubic, вычисляется парная разница метрик относительно baseline.

Используется двусторонний парный критерий Уилкоксона отдельно для PSNR-Y, SSIM-Y, PSNR-RGB и SSIM-RGB. Поправка Holm корректирует p-value с учётом множественных проверок. В CSV сохраняются число пар, медианная разница «метод минус baseline», статистика критерия, исходное p-value и скорректированное p-value.

Статистическая значимость не равна практической значимости: вместе с p-value нужно обсуждать размер эффекта, разброс по изображениям и стоимость по времени.

## Результаты

Файлы:
- metrics_per_image.csv — наблюдения по каждой паре «изображение—метод»;
- summary.csv — средние, стандартные отклонения, медианы метрик и времени;
- paired_tests_vs_bicubic.csv — статистическое сравнение с baseline;
- comparison_grid.png — визуальное сопоставление;
- run_metadata.json — параметры и среда.

Для финальной ВКР нужно сохранить результаты реального полного прогона, commit SHA и параметры фактически использованной Colab VM. Нельзя подменять результаты прогона предположительными цифрами.

## OCR и автомобильные номера — отдельный этап

DIV2K не является benchmark распознавания текста или номерных знаков. PSNR/SSIM не гарантируют, что OCR распознает символ лучше: небольшой сдвиг края или штриха может изменить символ при малом изменении общей пиксельной ошибки.

При прикладной постановке рекомендуется отдельная ветка:
1. выбрать реальный paired text dataset (например, TextZoom) или лицензированный dataset номерных знаков;
2. зафиксировать один OCR движок, версию модели и настройки;
3. прогнать все фильтры на одних LR изображениях;
4. измерить CER, WER/exact word accuracy либо exact plate accuracy;
5. приводить OCR метрики отдельно от PSNR/SSIM.

Авторы TextZoom отмечают, что синтетическое bicubic degradation не отражает реальные low-resolution текстовые изображения, получаемые при съёмке с разными фокусными расстояниями. Поэтому OCR проверку нельзя выводить из одного DIV2K эксперимента.
